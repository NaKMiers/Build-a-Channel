# Publishing Feedback Loop

Classification: `Core`

Scope: `CHANNEL_WIDE`

Purpose:
make every future `Why It Works` upload produce reusable learning for the next upload instead of treating performance as random luck.

This is a channel-wide system. It must not be filled out for an existing video unless the user explicitly asks to apply the system to that video project.

## Core Rule

After every upload, answer one question:

```text
What should change in the next video?
```

The answer must be specific enough to affect one of these areas:

- topic angle
- title
- thumbnail
- first `10-30` seconds
- WIT use
- explanation structure
- English learner clarity
- voice delivery
- visual texture
- music or sound
- production effort

If a lesson does not change a future decision, it is only an observation.

## Review Timing

Use three review moments when possible:

```text
24h: early packaging and hook signal
7d: first stable performance read
after next upload: did the lesson improve the next video?
```

Do not over-trust tiny numbers.
If analytics are too small, use the qualitative checklist and label the conclusion as low-confidence.

## Required Post-Upload Review

For each future published video, create one short post-upload review from:

[post-upload-review-template.md](post-upload-review-template.md)

Store the filled review in the relevant future video project only after that video project is explicitly active.
Do not create a review for any existing video unless the user asks.

## Metrics Checklist

Track these when available:

```text
[ ] impressions
[ ] click-through rate
[ ] views after 24h
[ ] views after 7d
[ ] average view duration
[ ] average percentage viewed
[ ] first 30s retention
[ ] biggest retention dips
[ ] traffic source
[ ] comments and repeated viewer reactions
[ ] questions or confusion from viewers
[ ] subs gained
```

Also track these qualitative signals:

```text
[ ] thumbnail looked clickable beside reference channels
[ ] title and thumbnail created one clear question
[ ] first 10 seconds paid off the package
[ ] first 30 seconds made the contradiction obvious
[ ] people who watched understood the main point
[ ] people who watched mentioned a joke, WIT moment, or visual
[ ] English learner clarity felt strong enough
[ ] production time was reasonable for the result
[ ] one asset, board pattern, joke pattern, or workflow step should become reusable
[ ] one workflow step should be simplified or removed
```

## Decision Rules

### If CTR Is Weak

Fix packaging before changing the whole format.

Check:

```text
[ ] thumbnail creates a question without needing the title
[ ] title names the hidden logic, not only the topic
[ ] title and thumbnail do not repeat the same information
[ ] thumbnail has one dominant object or situation
[ ] WIT emotion is clear at mobile size
[ ] package compares well beside reference channels
```

Likely next action:

- revise title-thumbnail logic
- test a stronger contradiction
- use a more concrete object
- make WIT emotion more specific

Do not conclude that the topic lane is bad from one weak CTR.

### If First `30s` Retention Is Weak

Fix hook and early contradiction first.

Check:

```text
[ ] topic is visible by second 3
[ ] contradiction is visible by second 5
[ ] WIT reaction appears early enough
[ ] first line sounds like a person, not an intro
[ ] no branding, definition, or setup delays the point
[ ] title-thumbnail promise is paid off by second 10
```

Likely next action:

- open with a situation instead of explanation
- show the consequence earlier
- add WIT reaction sooner
- remove polite setup
- make the first object more specific

### If Retention Drops Mid-Video

Find the section that became abstract, slow, or visually generic.

Check:

```text
[ ] section has a concrete real-life example
[ ] section has a visual joke or WIT reaction
[ ] section has one boardable idea
[ ] explanation length matches the payoff
[ ] voice does not outrun labels
[ ] labels are not too dense for English learners
```

Likely next action:

- add a real-life object or UI mockup
- cut one explanation layer
- replace a clean board with a funny evidence board
- repeat the key phrase more clearly
- move a payoff earlier

### If Comments Show Confusion

Fix clarity before adding more cleverness.

Check:

```text
[ ] main point is stated in simple English
[ ] key terms appear on screen
[ ] useful phrase is repeated naturally
[ ] idioms or cultural references are understandable from context
[ ] visual labels support the voice
[ ] joke does not hide the explanation
```

Likely next action:

- simplify sentence structure
- add clearer signposts
- repeat the main phrase
- make boards less crowded
- use a more direct example

### If Production Took Too Long

Improve the workflow before increasing ambition.

Check:

```text
[ ] custom animation created little viewer value
[ ] reusable asset should move into common assets
[ ] repeated board pattern should become a template
[ ] voice, captions, or timing took avoidable manual work
[ ] reference-board or source-note process was too late
```

Likely next action:

- move useful assets into the reusable library
- reduce custom animation
- use stronger static boards
- reuse WIT, red markup, real-life objects, and sound patterns
- simplify the next video's visual motif

## Learning Confidence

Use confidence labels:

```text
High: repeated across multiple uploads or backed by clear analytics and comments
Medium: supported by one upload plus strong qualitative evidence
Low: plausible but based on tiny analytics, personal taste, or one weak signal
```

Low-confidence lessons may guide experiments.
They must not rewrite core channel strategy.

## Next Video Rule

The next video should use at least one lesson from the previous upload.

The lesson must be visible in a concrete choice:

- sharper angle
- stronger thumbnail contradiction
- faster hook
- simpler learner-friendly phrasing
- clearer WIT role
- better real-life texture
- simpler production method

If no lesson is usable, write:

```text
No reusable lesson yet. Continue with the existing channel system.
```

## Learning Log Rule

Only write channel-level lessons into `docs/learning-log.md` if they are reusable beyond one video.

Use [channel-learning-rules.md](channel-learning-rules.md) before promoting observations into channel memory.

Allowed learning log categories:

- `Operational lesson`
- `Experiment result`
- `Packaging lesson`
- `Audience insight`

Do not rewrite `docs/channel-foundation.md` from upload performance unless the user explicitly confirms a core change.

## Acceptance Criteria

The feedback loop is working if:

- every future upload produces one short post-upload review
- the next video uses at least one lesson from the previous upload
- repeated problems become workflow rules
- strong assets become reusable assets
- weak assumptions are labeled and tested instead of becoming strategy
- analytics improve decisions without replacing creator judgment

## Working Standard

```text
Measure the upload. Learn one useful thing. Change the next video.
```
