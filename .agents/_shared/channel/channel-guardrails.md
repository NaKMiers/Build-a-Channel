# Channel Guardrails

This file protects `Why It Works` from accidental self-sabotage.

Its purpose is simple:

- Bad ideas should not become official strategy
- Temporary moods should not rewrite the channel
- Risky experiments should be labeled as experiments
- Core identity changes should require a pause and explicit confirmation

## Core Rule

Future Codex sessions must **not** write new channel strategy into the core docs unless the idea passes the checks below.

If an idea fails these checks, it should either:

- be rejected
- stay only in chat
- or be stored as a `possible experiment`, not as a core decision

## Three Buckets

Every meaningful new idea should be classified into one of these buckets before it is written into project docs.

### 1. Core

Write into core docs only if the idea is:

- strongly aligned with channel identity
- low-risk to trust and brand clarity
- useful beyond one moment
- something we would still want to stand by later

### 2. Experiment

Write into the learning log as an experiment if the idea is:

- interesting but uncertain
- potentially useful but not yet proven
- something that needs testing before becoming strategy

Label clearly as:

- `experiment`
- `hypothesis`
- `test`
- `temporary idea`

### 3. Reject

Do not write into the project docs if the idea is:

- off-brand
- harmful to trust
- low-quality clickbait
- emotionally impulsive
- legally risky
- too far from the channel promise

## The Safety Checks

Before writing a new idea into the project files, check:

### 1. Brand Fit

Does this fit `Why It Works` as:

- English-first
- no-face
- funny explainer
- learner-friendly for English learners
- focused on money, internet, society, business, and modern life

If not, it should not enter core strategy.

### 2. Audience Fit

Will this help the target audience, or confuse them?

The primary audience lens is now English learners who want interesting real-world English, not boring lessons.

If it makes the audience ask:

- `Why is this channel doing this now?`
- `What is this channel even about?`

then it is probably a bad core move.

### 3. Trust Fit

Does this improve trust, or damage it?

Avoid anything that relies on:

- misleading framing
- fake authority
- low-effort outrage bait
- dishonest storytelling
- inflated claims

### 4. Sustainability Fit

Can this be repeated consistently, or is it just exciting once?

Do not put one-off impulses into core strategy.

### 5. Quality Fit

Would this make the channel feel sharper, clearer, and more distinct?

If it makes the channel feel noisier, more generic, more desperate, or more confusing, reject it.

### 6. Long-Term Fit

Would we still be happy this is in the docs after 6 months?

If not, it should not become official.

## High-Risk Changes That Require Explicit Confirmation

Codex must pause and ask for explicit confirmation before changing any of these in the core docs:

- channel name
- primary language
- no-face format
- main audience
- core promise
- main content pillars
- voice and tone
- relationship to Deewas
- monetization direction
- visual identity direction

These are foundational. They should not drift casually.

## Red Flags

If a future idea contains any of these patterns, Codex should challenge it before writing it down:

- `Let's copy this creator exactly`
- `Let's chase views even if it confuses the brand`
- `Let's change topics every week`
- `Let's make rage bait`
- `Let's promise things we can't deliver`
- `Let's turn the channel into direct app promotion`
- `Let's abandon the English-first direction without a strong reason`
- `Let's switch the whole brand because one idea sounds exciting today`

## What To Do With Uncertain Ideas

If an idea is not clearly good or clearly bad:

1. Keep it out of the core docs
2. Put it in the learning log as an experiment
3. State what would need to be true for it to become a real strategy

Example:

`Experiment: test whether more culture-led topics outperform money-led topics over 5 uploads.`

That is much safer than rewriting the whole channel positioning.

## Default Protection Rule

When uncertain, prefer:

- preserving the current strategy
- labeling ideas as experiments
- asking before changing foundations

Not every idea deserves persistence.

## Practical Rule For Future Codex Sessions

Before writing a new strategic idea into project files, Codex should silently ask:

- Is this core, experiment, or reject?
- Does this strengthen the channel?
- Does this protect trust?
- Does this still fit `Why It Works`?

If the answer is weak or unclear, do not store it as core strategy.
